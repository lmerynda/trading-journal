# ADR 0001: Store screenshots in Railway Storage Buckets

- Status: accepted
- Date: 2026-07-19

## Context

Screenshots are first-class review evidence and will accumulate for the life of the product. They must load efficiently on public reviews and stay separate from relational application data.

The application is expected to remain on Railway for the foreseeable future. Introducing another infrastructure provider during the MVP would add credentials, billing, deployment configuration, and operational failure modes without providing a meaningful near-term benefit.

At the same time, the application should not embed Railway-specific URLs or APIs throughout its domain model.

## Decision

Use a private Railway Storage Bucket for screenshot originals and generated display variants. Use PostgreSQL for screenshot metadata and object references.

For the MVP, uploading remains conventional: the browser sends a multipart file upload to a Next.js route handler, which validates the image, writes it to Railway, and stores its database reference. This keeps the first implementation and its failure handling easy to understand.

Presigned direct uploads or downloads may be introduced later as an internal bandwidth optimization. They do not change what the user sees or how screenshots are represented in the database.

Access to object storage is implemented behind an S3-compatible TypeScript interface:

```ts
interface ObjectStorage {
  put(input: PutObjectRequest): Promise<StoredObject>;
  get(key: string): Promise<ReadableStream>;
  stat(key: string): Promise<ObjectMetadata>;
  delete(key: string): Promise<void>;
}
```

The interface may grow only for demonstrated application requirements. Provider administration and bucket creation remain deployment concerns rather than domain capabilities.

## Database responsibility

PostgreSQL stores:

- An opaque, immutable object key.
- Owning user and trade image record.
- Screenshot role: entry context, outcome, or supporting.
- Primary/display ordering.
- Original filename and MIME type.
- Width, height, and byte size.
- Content hash for integrity and duplicate detection.
- Upload state and timestamps.
- Optional derived-variant keys.

PostgreSQL does not store image binaries, permanent presigned URLs, Railway endpoint URLs, or storage credentials.

## Object layout

Object keys are generated by the application and contain random identifiers rather than user-controlled filenames:

```text
reviews/{dailyReviewId}/images/{imageId}/original
reviews/{dailyReviewId}/images/{imageId}/display.webp
reviews/{dailyReviewId}/images/{imageId}/thumbnail.webp
```

The database remains the authority connecting objects to public day and trade pages. Knowledge of an object key alone is not part of the supported application interface.

## Upload flow

1. The authenticated client posts the screenshot as ordinary multipart form data.
2. The Next.js route handler validates administrator access, type, and size.
3. The server writes the object to Railway through the storage adapter.
4. The server creates the database image record with its opaque object key and metadata.
5. The route returns the attached image record to the client.
6. A job may later create display and thumbnail variants while preserving the original.

If the object write succeeds but the database write fails, cleanup is retried safely. A scheduled reconciliation job removes objects that remain unattached.

## Read flow

Day, trade, and associated screenshot reads are public. Creating, replacing, or deleting screenshots requires administrator authentication.

The initial Next.js application may proxy object reads for implementation simplicity. If bandwidth or public traffic becomes material, the adapter can issue object URLs without changing database records or product behavior.

## Image policy

- Preserve the original upload as the review source of truth.
- Generate a review-sized display image and a smaller library thumbnail when beneficial.
- Test compression against real annotated screenshots because small chart labels must remain legible.
- Enforce MIME, dimension, and byte-size limits before attaching an upload.
- Never automatically expire originals belonging to active reviews.
- Lifecycle cleanup applies only to abandoned uploads and unreferenced generated objects.
- Deletion is initiated from the database record, with object cleanup retried safely.

## Local development

Use an S3-compatible local object store such as MinIO. Tests may use an in-memory fake for domain-independent cases, but upload integration tests should exercise the real S3-compatible behavior.

## Consequences

### Benefits

- One production provider during the MVP.
- Conventional uploads keep the MVP implementation and user-visible behavior simple.
- Screenshot data remains outside PostgreSQL backups and transaction load.
- S3 compatibility preserves a practical path to R2, B2, S3, or another provider.

### Costs and limitations

- Production storage availability and billing are initially coupled to Railway.
- Uploads, downloads, and image-processing jobs routed through Railway services may incur service egress until direct presigned transfers are introduced.
- The team must back up both PostgreSQL metadata and object storage; one without the other is incomplete.
- Moving providers still requires copying and verifying objects even though application code remains largely unchanged.

## Migration strategy

If migration becomes necessary:

1. Create the destination S3-compatible bucket.
2. Copy objects while preserving keys and metadata.
3. Verify object counts, sizes, and hashes.
4. Dual-write new uploads during the cutover if the library is active.
5. Change storage adapter configuration.
6. Retain Railway objects for a defined recovery window before deletion.

No relational schema change should be required because the database stores opaque keys rather than provider URLs.
